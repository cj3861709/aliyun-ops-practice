## 分段约定

```
  0 - 1023      系统保留（22 / 80）
1024 - 7999      未使用（保留给未来的标准服务）
8000 - 8099      应用服务区（nginx / Tomcat / 代理）
8100 - 8999      预留
9000 - 9999      练习与临时环境
3306 / 6379       数据库与缓存（仅本机）
```

### 为什么这样分段

| 分段 | 理由 |
|---|---|
| **0-1023** | 特权端口，需要 root 才能绑定 |
| **8000-8099** | 应用服务连续分配，便于记忆 |
| **9000-9999** | 与生产/常规服务区分，一眼能看出是"练习环境" |

## 绑定地址的原则

**默认只绑本机（`127.0.0.1`），除非有明确的外部访问需求。**

| 绑定 | 什么时候用 |
|---|---|
| **`127.0.0.1`** | 只有同机服务需要访问（数据库、缓存、后端应用） |
| **`0.0.0.0`** | 确实需要从外部访问（Web 前端） |

**为什么这是原则**：

```
绑 0.0.0.0 → 依赖【安全组】一层防护
                ↓ 安全组规则被误改
             立即暴露

绑 127.0.0.1 → 安全组 + 绑定地址【两层防护】
                ↓ 安全组规则被误改
             仍然不可达
```

**这是"纵深防御"在端口层面的应用。**

## 已知问题与改进方向

### 问题 1：Tomcat 绑在所有网卡

```
当前:  *:8082（IPv4 + IPv6 全部）
建议:  127.0.0.1:8082
```

**为什么不紧急**：安全组未放行，公网不可达。

**为什么要改**：

| 理由 | 说明 |
|---|---|
| **单点依赖** | 当前只有安全组一层防护 |
| **无需外部访问** | 只有同机 nginx 需要连它 |
| **一致性** | MariaDB / Redis 都只绑本机，Tomcat 应该对齐 |

**修改方式**（`/etc/tomcat/server.xml`）：

```xml
<Connector port="8082" protocol="HTTP/1.1"
           address="127.0.0.1"        <!-- 新增这行 -->
           connectionTimeout="20000"
           redirectPort="8443"
           maxParameterCount="1000"
           />
```

### 问题 2：练习端口与生产端口混在 80xx 段

```
当前:  8081(lab01) 8082(Tomcat) 8083(代理) 8090(quest01) 都是 80xx
       9090(lab02) 在 9xxx

建议:  生产类 → 80xx
       练习类 → 9xxx
```

**影响**：看到端口号无法判断是"生产服务"还是"练习环境"。

**改进建议**（如果将来重排）：

```
8080  生产站点测试口
8082  Tomcat
8083  反向代理

9081  练习 lab01（原 8081）
9090  练习 lab02（不变）
9091  练习 quest01（原 8090）
```

**暂不执行** —— 因为改动涉及 nginx 配置、练习脚本、检查器多处，
收益不足以抵消风险。**记录下来作为将来的整理方向。**

### 问题 3：8080 的语义模糊

```
8080 现在 = nginx 测试站点
8080 常识 = Tomcat 默认端口
```

**影响**：看到 8080 容易误判为 Tomcat。

**缓解方式**：在文档里明确标注（本表中已体现）。

## 端口冲突排查方法

**部署新服务前，先查端口是否被占用**：

```bash
# 方法 1：查特定端口
ss -tlnp | grep ':端口号'

# 方法 2：列出所有监听端口
ss -tlnp

# 方法 3：检查端口范围是否空闲
for p in 8080 8081 8082 8083; do
    if ss -tln | grep -q ":$p "; then
        echo "$p 已占用"
    else
        echo "$p 空闲"
    fi
done
```

**如果服务启动后端口未监听**（常见的静默故障）：

```bash
# 1. 服务状态（可能是假正常）
systemctl status <服务>

# 2. 实际监听的端口
ss -tlnp | grep <进程名>

# 3. 日志里的绑定错误
journalctl -u <服务> | grep -iE 'bind|address already|severe'

# 4. 确认访问到的是哪个服务（关键）
curl -I http://127.0.0.1:<端口>/
# 看 Server 响应头：nginx 会发，Tomcat 默认不发
```

**经验**：Tomcat 的 8080 冲突曾导致「服务 active 但功能不可用」——
主进程因 shutdown 端口绑定成功而存活，systemd 报告正常，
但 HTTP 连接器实际未启动。（见手记 008）

## 安全组配置对照

**公网可达的端口（最小化原则）**：

| 端口 | 是否需要公网访问 | 说明 |
|---|---|---|
| 22 | ✅ 需要 | SSH 管理 |
| 80 | ✅ 需要 | Web 站点 |
| 8080 | ✅ 需要 | 备案期间用 IP 访问 |
| 其余 | ❌ 不需要 | 保持关闭 |

**8080 的临时性**：

备案通过、域名可访问后，**8080 应该关闭** ——
因为它只是备案期间的替代入口。

```bash
# 备案后可从安全组删除 8080 规则
# 届时只需保留 22（SSH）+ 80（HTTP）+ 443（HTTPS）
```

## 维护约定

**新增服务时的流程**：

```
1. 查本文档，选一个未占用的端口
2. 判断是否需要公网访问
   · 需要 → 绑 0.0.0.0 + 在安全组放行
   · 不需要 → 绑 127.0.0.1
3. 部署后更新本文档的端口表
4. 提交到 Git
```

**为什么要有这个约定**：

端口是**全局共享资源**，冲突会导致服务起不来或功能异常。
文档化能避免"部署时才发现端口被占"。
