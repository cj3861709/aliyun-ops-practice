# 运维命令速查 + 排查方法论

> 这份手册按「**我要回答什么问题**」组织，不是按字母顺序。
> 排查时先想"我现在要回答什么"，再找对应的命令。

---

# 第一部分：排查方法论

## 核心循环（四步）

```
┌─────────────────────────────────────────────┐
│  1. 确认现象    到底哪里"不对"？给出具体依据  │
│       ↓                                     │
│  2. 缩小范围    排除掉不可能的部分            │
│       ↓                                     │
│  3. 定位根因    找到"为什么"                 │
│       ↓                                     │
│  4. 验证修复    用【功能】验证，不是看命令返回 │
└─────────────────────────────────────────────┘
         ↑                                │
         └────────── 没修好就回到 1 ────────┘
```

## 关键原则

### 原则 1：先确认现象，不要急着改

**新手最常见的错误**：看到"服务有问题"就 `systemctl restart`。

**为什么错**：
- 重启可能让问题暂时消失 → 你永远不知道根因
- 问题会再犯
- 面试官问"为什么坏"，你答不上来

**正确做法**：先收集证据，**保持现场**。

### 原则 2：一次只改一个东西

如果你同时改了权限、配置、重启了服务，然后好了 —— **你不知道是哪个改对了**。

**正确做法**：改一个 → 验证 → 记录结论 → 再改下一个。

### 原则 3：区分「状态正常」和「功能正常」

**这是本次任务的核心。**

```bash
systemctl is-active nginx      # 说"active"
# 不代表：
#   · 端口在监听
#   · 能返回正确内容
#   · 后端还活着
```

| 检查层次 | 命令 | 说明 |
|---|---|---|
| 进程存在 | `systemctl is-active X` | 最弱 |
| 端口监听 | `ss -tlnp` | 中等 |
| 能响应 | `curl -I` | 较强 |
| **功能正确** | `curl` 看内容 / 看输出变化 | **最强** |

**排查时要从最强的层次开始验证。**

### 原则 4：怀疑"静默失败"

**最危险的故障不报错。**

看这个例子：

```bash
echo "内容" >> /var/log/app.log 2>/dev/null
                                 ↑
                        错误被丢进 /dev/null
                        写失败了你也不知道
```

**症状**：服务状态正常，但**没有任何产出**。

**怎么发现**：不要看"命令有没有报错"，要看"**产出有没有变化**"。

### 原则 5：用时间维度判断

**很多问题靠"时间差"暴露**：

```bash
# 日志最后修改时间 vs 当前时间
ls -la /var/log/app.log      # 显示 Sep 16 13:27
date                          # 显示 Sep 16 14:30
# → 差了一个小时，说明日志早就停止更新了
```

**这是发现"静默失效"最快的方法。**

# 第二部分：命令速查

## A. 我要看「服务是否在运行」

```bash
systemctl is-active <服务名>          # active / inactive / failed
systemctl is-enabled <服务名>         # enabled / disabled
systemctl status <服务名>             # 详细状态（含最近日志）
systemctl --failed                    # 列出所有失败的服务
```

**注意**：`is-active` 返回 `active` **只说明进程存在**，不代表功能正常。

---

## B. 我要看「服务的日志」

```bash
# systemd 收集的日志（应用输出到 stdout/stderr 的部分）
journalctl -u <服务名> -n 50 --no-pager        # 最近 50 行
journalctl -u <服务名> --since "10 min ago"    # 最近 10 分钟
journalctl -u <服务名> -f                       # 实时跟踪
journalctl -u <服务名> -p err                   # 只看错误级别

# 应用自己的日志文件
tail -20 /var/log/xxx.log
tail -f /var/log/xxx.log                        # 实时跟踪
```

**区别很重要**：
- `journalctl` 看的是 systemd 收集的
- `tail` 看的是应用**自己写的文件**

**两者可能不一致** —— 比如应用写文件失败时，journal 里可能什么都没有（因为错误被吞了）。

---

## C. 我要看「端口是否被监听」

```bash
ss -tlnp                    # TCP 监听端口 + 进程
ss -tlnp | grep 8080        # 过滤特定端口
ss -tunlp                   # 加上 UDP
```

**输出解读**：
```
LISTEN 0 128 0.0.0.0:8080 0.0.0.0:* users:(("nginx",pid=1234,fd=6))
             └────┬────┘
           监听地址:端口
```

| 监听地址 | 含义 |
|---|---|
| `0.0.0.0:80` | 所有网卡（外部可达） |
| `127.0.0.1:80` | 仅本机（外部不可达） |
| `[::]:80` | IPv6 所有网卡 |

---

## D. 我要看「服务以什么身份运行」

```bash
# 方法 1：查主进程的属主
ps -o user,pid,cmd -p $(systemctl show <服务名> -p MainPID --value)

# 方法 2：查 unit 文件里声明的
systemctl show <服务名> -p User -p Group

# 方法 3：看进程树（含子进程）
systemctl status <服务名> | grep -A5 CGroup
```

**为什么重要**：服务能读写什么文件，**完全取决于它的身份**。

---

## E. 我要看「文件的权限和属主」

```bash
ls -la /path/to/file                    # 基本权限
stat /path/to/file                      # 详细信息（含 inode、时间）
stat -c '%A %U:%G %n' /path/to/file     # 定制输出：权限 属主 文件名

# 看路径上每一级的权限（关键！）
namei -l /var/log/app.log
```

**`namei -l` 的重要性**：

权限要**沿路径逐级检查**。任何一级目录缺 `x`，访问就失败。

```
$ namei -l /var/log/app.log
dr-xr-xr-x root root /          ← 可进入
drwxr-xr-x root root var        ← 可进入
drwxr-xr-x root root log        ← 可进入
-rw-r--r-- root root app.log    ← 文件本身
```

**只看最后一行的 `ls -l` 是不够的。**

---

## F. 我要「以另一个用户的身份验证权限」

```bash
# 测试可读
sudo -u <用户> test -r /path/to/file && echo "可读" || echo "不可读"

# 测试可写
sudo -u <用户> test -w /path/to/file && echo "可写" || echo "不可写"

# 测试可进入目录
sudo -u <用户> test -x /path/to/dir && echo "可进入" || echo "不可进入"

# 实际执行命令
sudo -u <用户> <命令>
```

**这一条是排查权限问题的**决定性手段**。比看权限位可靠得多。**

---

## G. 我要看「磁盘和 inode」

```bash
df -h                    # 磁盘空间
df -i                    # inode 使用率（inode 耗尽也会导致写入失败！）
du -sh /var/log/*        # 各目录占用
```

**inode 耗尽的症状**：`df -h` 显示有空间，但创建文件报 `No space left on device`。

---

## H. 我要看「文件是否在被写入」

```bash
# 看修改时间（最快的方法）
ls -la /var/log/app.log
stat -c '%y %n' /var/log/app.log

# 隔一段时间对比行数
wc -l /var/log/app.log
sleep 60
wc -l /var/log/app.log     # 有增长说明在写

# 用 watch 持续观察
watch -n 5 'ls -la /var/log/app.log; tail -3 /var/log/app.log'
```

---

## I. 我要看「谁在用这个文件」（含被删除的）

```bash
# 某个文件被哪些进程打开
lsof /var/log/app.log

# 已删除但仍被占用的文件（磁盘空间泄漏的元凶）
lsof | grep deleted

# 某个目录被哪些进程使用
lsof +D /var/log
```

**注意**：本机 `lsof` 未安装。可用替代：

```bash
# 用 /proc 查找
for p in /proc/[0-9]*; do
  ls -l $p/fd 2>/dev/null | grep -q "app.log" && \
    echo "$(cat $p/comm) (pid=$(basename $p))"
done
```

---

## J. 我要看「文件系统事件」（进阶）

```bash
# 用 stat 的 inode 号追踪文件是否被替换
stat -c '%i %n' /var/log/app.log
# 记录 inode 号 → 做某操作 → 再查 → 号变了说明文件被替换

# 用 inotify 实时监控（需安装 inotify-tools）
inotifywait -m /var/log/app.log
```

---

## K. 我要看「定时任务」

```bash
# 用户 crontab
crontab -l

# 系统 cron 任务
cat /etc/crontab
ls -la /etc/cron.d/
ls -la /etc/cron.daily/ /etc/cron.hourly/

# systemd timer
systemctl list-timers --all

# cron 是否执行过
journalctl -u crond --since today | tail -20
```

---

## L. 我要看「日志轮转」

```bash
# 轮转配置
cat /etc/logrotate.d/<服务名>
cat /etc/logrotate.conf            # 全局策略

# 轮转产生的文件
ls -la /var/log/app.log*

# 轮转状态记录（记录上次轮转时间）
cat /var/lib/logrotate/logrotate.status

# 手动触发轮转
logrotate -f /etc/logrotate.d/<服务名>

# dry-run（只显示不执行）——【排查时非常有用】
logrotate -d /etc/logrotate.d/<服务名>
logrotate -d -f /etc/logrotate.d/<服务名>    # 强制演示
```

**`-d` 是排查神器**：它会把"打算做什么"全部打印出来，包括：
```
creating new /var/log/app.log mode = 0644 uid = 1000 gid = 1000
                                        └──────┬──────┘
                                        新文件的属主 ← 关键信息
```

---

## M. 我要看「进程详情」

```bash
ps aux | grep <关键词>
ps -eo pid,ppid,user,cmd | grep <关键词>

# 进程树
pstree -p <PID>

# 进程的打开文件
ls -l /proc/<PID>/fd/

# 进程的环境变量
cat /proc/<PID>/environ | tr '\0' '\n'
```

---

## N. 我要看「系统资源」

```bash
free -m                   # 内存
uptime                    # 负载
top / htop                # 实时资源
vmstat 1 5                # 系统整体状态
```

---

## O. 我要看「网络连接」

```bash
ss -tnp                              # 已建立的 TCP 连接
ss -tnp state established            # 同上
ss -s                                # 连接统计

# 测试接口
curl -I http://127.0.0.1:8080/       # 只看响应头
curl -s http://127.0.0.1:8080/ | head  # 看内容
curl -v http://127.0.0.1:8080/       # 详细过程
```

# 第三部分：排查清单（按顺序做）

**遇到"服务有问题"时，按这个顺序走：**

## 第 1 组：确认现象

```bash
# 1. 服务状态
systemctl status <服务名>

# 2. 日志最后修改时间 vs 当前时间 ← 发现静默失效的关键
ls -la /var/log/<日志文件>
date

# 3. 日志内容（最后几行）
tail -20 /var/log/<日志文件>
```

**回答**：到底哪里"不对"？日志停在什么时间？现在是什么时间？

## 第 2 组：排除"进程死了"

```bash
# 4. 进程是否存在
systemctl is-active <服务名>

# 5. 进程身份
ps -o user,pid,cmd -p $(systemctl show <服务名> -p MainPID --value)

# 6. 端口是否监听
ss -tlnp | grep <端口>
```

**回答**：进程活着吗？以什么身份？端口在监听吗？

## 第 3 组：检查"能不能写"

```bash
# 7. 文件属主和权限
stat -c '%A %U:%G %n' /var/log/<日志文件>

# 8. 【关键】以服务身份测试可写
sudo -u <服务用户> test -w /var/log/<日志文件> && echo "可写" || echo "不可写"

# 9. 路径权限链
namei -l /var/log/<日志文件>
```

**回答**：服务身份能写这个文件吗？

## 第 4 组：检查"是否有东西改了它"

```bash
# 10. 日志轮转配置
cat /etc/logrotate.d/<服务名>

# 11. 轮转产生的文件（有没有异常）
ls -la /var/log/<日志文件>*

# 12. 最近轮转时间
cat /var/lib/logrotate/logrotate.status | grep <日志名>
```

**回答**：最近有轮转吗？轮转配置正确吗？

## 第 5 组：修复

```
1. 修复当下问题（让服务现在就能工作）
2. 修复根因（防止再犯）
3. 重启服务（如果必要）
4. 验证：等 1-2 分钟，确认【产出】真的在增加
5. 预防验证：确认下次轮转不会再犯（用 dry-run）
```

---

# 第四部分：修复后的验证清单

**"改完了"不等于"修好了"。**

| 验证层次 | 怎么做 |
|---|---|
| 命令成功 | 看命令返回 0 |
| 状态正确 | `systemctl is-active`、`stat` 看权限 |
| **功能正常** | **等 1-2 分钟，看产出是否增加** |
| 根因已修 | 检查配置源头，而不只是当前文件 |
| 不会复发 | 用 dry-run 或模拟触发，确认下次也正常 |

**本次任务至少要做到第 3 层和第 5 层。**

# 附：本机特有注意事项

| 项目 | 说明 |
|---|---|
| `lsof` 未安装 | 用 `/proc/<pid>/fd` 替代 |
| `vim` 被 Workbench AI 拦截 | 用 `nano`，或者让助手代写 |
| 日志轮转有 `dateext` | 轮转后是 `.log-20260916` 形式，不是 `.log.1` |
| 服务 `quest02` | 心跳服务，写 `/var/log/quest02.log` |
| 生产站点 | 80/8080 端口，**不要动** |
| 练习站点 | 8090 端口（quest01） |
