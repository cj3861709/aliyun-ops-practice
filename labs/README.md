# 运维练习实验室

带**自动判分**的动手练习。判分检查**系统实际状态**，不检查你敲过什么命令 ——
你可以用任何方法达成目标，那才是真实运维。

## 快速开始

```bash
lab list          # 列出所有练习
lab show 01       # 查看练习说明
lab check 01      # 判分
lab hint 01       # 渐进式提示（一次给一条，强制你先自己想）
lab reset 01      # 重置环境，重做一遍
```

## 练习 01 的关键考点：端口冲突

生产站点已占用 80 和 8080。如果你也配 8080 且 `server_name` 相同：

```
$ nginx -t
[warn] conflicting server name "_" on 0.0.0.0:8080, ignored
configuration file /etc/nginx/nginx.conf test is successful   ← 看起来没问题

$ curl http://127.0.0.1:8080/
# 返回【生产站点】，你的配置被静默忽略了
```

**这个现象教三件事**：
1. `nginx -t` 的 warning 不能忽略
2. "语法正确" ≠ "行为符合预期"
3. 遇到端口占用，先查谁在用，再决定换端口还是协商

## 练习 02 的关键考点：排查方法论

故障现象：**服务 active、端口在听，但访问返回 403**。

正确的排查顺序：

```
现象（状态码）→ 服务层（active?监听?）→ 日志（error.log）
→ 具体原因（权限）→ 验证假设 → 修复 → 再验证
```

判分**强制你写排查记录**（`findings.md` 要有现象/排查过程/根因/修复四节）。
不要求写得多好，要求真的去查 —— 因为面试时你能讲出多少细节，
取决于你记录了多少。

## 判分脚本的设计原则

1. **检查状态而非历史** —— 不看你敲了什么命令
2. **真实验证行为** —— 练习 01 会真的 `kill -KILL` nginx，验证能否自愈
3. **可独立运行** —— `bash labs/01/check.sh` 也能跑（不依赖 lab.sh）
4. **双向验证** —— 不仅验证"正确的能通过"，也验证"错误的能被检出"
5. **给具体线索** —— 失败时指出差在哪、怎么验证，而不只是报红

## 设计这些练习时的自我审查

我在第 11 轮做了一次**老师试做**，发现问题：

| 发现的问题 | 后果 | 修复 |
|---|---|---|
| 练习 01 用 8080，与生产站点冲突 | **学生永远无法通过，且原因不可见** | 改用 8081，并把冲突变成显式考点 |
| 判分脚本 `check_ok: command not found` | 无法独立运行、无法单独测试 | 加入自包含引导代码 |
| 冲突检测误报 | 明明用 8081 却报"使用了 8080" | 只检查未注释的 `listen` 指令 |

**教训：写练习和写代码一样，必须实测。**
"设计上应该可行"和"实际可解"是两件事 ——
这和项目里复盘 #004 的教训完全一致。
