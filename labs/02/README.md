# 练习 02：服务起不来，你来排障

**难度**: ⭐⭐⭐☆☆ （中级）
**预计时间**: 30-50 分钟
**前置**: 建议先完成练习 01

---

## 背景故事

同事交给你一台服务器，说"**网站打不开了，我查了一下服务是 active，但访问就是不行**"。

你接手后需要：**找到根因、修复它、并说明为什么**。

```bash
# 复现问题
curl http://127.0.0.1:9090/    # 访问失败
```

---

## 你要做的事

- [ ] **找到根因**（不是猜，要有证据）
- [ ] **修复问题**，让 `http://127.0.0.1:9090/` 返回 200
- [ ] 站点内容要包含字符串 `LAB02-OK`
- [ ] **写下排查过程**（会判分你有没有记录）

---

## 关键要求：写下你的排查过程

这个练习**不只看结果，还看过程**。你需要把排查记录写到：

```
/root/ops-lab/labs/02/findings.md
```

格式要求（**必须**包含这几节）：

```markdown
## 现象
（你看到了什么？具体的命令和输出）

## 排查过程
（你依次检查了什么？每一步的结论是什么？）

## 根因
（最终确定的原因，以及支持这个结论的证据）

## 修复
（你改了什么？为什么这么改？）
```

> 判分脚本会检查这个文件是否存在、是否包含这四节。
> **不要求写得多好，要求真的去查。**

---

## 这台服务器的"案情"

提醒你几个**可能的**方向（不是全部，也不是答案）：

- 服务状态显示 active，但端口没有响应 —— 这说明什么？
- 日志里有没有线索？`journalctl`、`error.log`、`access.log`
- 配置文件的权限、属主对不对？
- 监听地址是 `0.0.0.0` 还是 `127.0.0.1`？有区别吗？
- 有没有可能"服务活着，但它监听的端口不是你以为的那个"？

---

## 重要：不要用 restart 蒙混过关

如果你一上来就 `systemctl restart`，问题可能会**暂时消失**，
但你**不知道根因** —— 而且它可能会再犯。

**排查的正确顺序**：

```
1. 先观察现状（不要急着改）
2. 收集证据（日志、端口、进程、配置）
3. 形成假设
4. 验证假设（用小实验证明或推翻）
5. 修复
6. 确认修复（并且说明"为什么会发生"）
```

这个顺序在面试时非常重要 ——
面试官问"你怎么排障"时，他期待的就是这套方法论。

---

## 判分

```bash
lab.sh check 02
```

判分会检查：
1. 9090 端口是否正常返回 200
2. 内容是否含 `LAB02-OK`
3. `findings.md` 是否存在且包含四节结构

**注意**：判分**不检查**你是否用了某个命令。
但你如果只是 restart 了一下，`findings.md` 里会写不出真正的根因 ——
那这一项的价值就没了。**这个练习的核心是思维方式，不是结果。**

## 做完之后

对比一下你的排查过程，和项目里复盘 #002 的思路：

```
/root/ops-lab/docs/postmortem/002-nginx-config-validate.md
```

注意它是怎么写的：
- **第一反应（错的）** —— 诚实地记录自己的错误猜测
- **真正的根因** —— 用证据推翻自己
- **最重要的部分** —— 安全网如何起作用

**这种"敢于记录自己判断错了"的复盘，比只写成功结果的记录有价值得多。**
面试时讲这个，比讲"我配了个 nginx"有说服力。
